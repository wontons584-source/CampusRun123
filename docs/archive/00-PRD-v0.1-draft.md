## 1. 背景与目标

### 1.1 背景

校园内存在稳定且高频的「最后一公里」需求：快递点集中在 2～3 个驿站，学生下课时间与驿站营业时间冲突；代买（食堂、超市、打印店）与代送（材料、钥匙、证件）需求零散但持续存在。现有解决方式是微信群喊单，存在四个结构性问题：

1. **匹配靠运气**：消息被刷走，发单人不知道谁在附近、能否接。
2. **无履约保障**：没有状态记录，丢件、超时、赖账无据可查。
3. **无身份约束**：校外人员可混入群，安全边界为零。
4. **无沉淀**：跑腿经历、信誉、评价全部不可复用。

### 1.2 产品目标

用「学号本校认证 + 地理位置智能推送 + 状态机化履约」把微信群喊单升级为可追溯、可评价、可治理的交易闭环。

### 1.3 成功指标（North Star 与护栏）

| 类型 | 指标 | 目标（上线 8 周） |
|---|---|---|
| 北极星 | 周成单量（COMPLETED） | ≥ 300 单/周 |
| 核心 | 发单→接单中位时长（TTFG） | ≤ 8 分钟 |
| 核心 | 推送触达→抢单转化率 | ≥ 12% |
| 核心 | 订单完成率（完成 / 有效发单） | ≥ 85% |
| 护栏 | 纠纷率（DISPUTED / 完成单） | ≤ 3% |
| 护栏 | 推送打扰投诉率 | ≤ 0.5% |
| 护栏 | 平均接单响应（接单→首次进度） | ≤ 15 分钟 |

### 1.4 非目标（本期明确不做）

- 跨校区 / 跨校订单；校外代取；夜间（23:00–07:00）配送。
- 专职跑腿者体系与派单制（本期是**抢单制**，不是派单制）。
- 平台自营资金池、骑手保险、发票。资金方案见 16.1。
- 路线规划与实时轨迹回放（V2 考虑，本期只做位置上报与距离计算）。

## 2. 角色与权限

| 角色 | 说明 | 关键权限 |
|---|---|---|
| 游客 | 未登录 | 浏览落地页、提交认证申请 |
| 待认证用户 | 已注册未通过学号认证 | 仅个人中心，不能发单/抢单 |
| 认证用户（发单人） | 通过本校认证 | 发单、取消、确认、评价、投诉 |
| 认证用户（接单人） | 同上，同一账号可切换身份 | 抢单、更新进度、送达、查看接单记录 |
| 运营管理员 | 校级运营 | 订单查询/干预、用户封禁、纠纷仲裁 |

> 设计原则：**发单人与接单人是同一类账号的两种行为**，不做双角色注册。用户可在「我的」里切换接单模式（开启后才上报位置、才被召回）。

## 4. 订单状态机（对原始需求的一处必要纠正）

### 4.1 结论

原始需求给的是三态（待接单 / 进行中 / 已完成）。**三态在数据上能存，但在业务上不成立**：发单人「确认」这个动作没有承接状态——接单人点「已送达」和发单人「确认」会挤在同一个「进行中」里，导致三个问题无法解决：

- 无法区分「接单人声称送达」与「发单人认可送达」，纠纷时无责任分界；
- 无法实现超时自动确认（没有「待确认」这个计时起点）；
- 无法统计真实履约时长（送达时间点丢失）。

因此扩为 **4 个主状态 + 3 个异常/终态**，对外展示时仍可折叠成用户看到的三个进度节点（待接单 → 进行中 → 已完成），不增加用户心智负担。

### 4.2 状态定义

| 状态 | 枚举值 | 对外文案 | 进入条件 |
|---|---|---|---|
| 待接单 | `PENDING` | 待接单 | 发单成功 |
| 进行中 | `IN_PROGRESS` | 进行中 | 接单人抢单成功 |
| 待确认 | `DELIVERED` | 待确认 | 接单人点「已送达」 |
| 已完成 | `COMPLETED` | 已完成 | 发单人确认 / 24h 超时自动确认 |
| 已取消 | `CANCELLED` | 已取消 | 发单人取消（PENDING 直接取消；IN_PROGRESS 需接单人同意或客服介入） |
| 已过期 | `EXPIRED` | 无人接单 | PENDING 超过 deadline 且未接单，系统关闭 |
| 纠纷中 | `DISPUTED` | 处理中 | 任一方在 COMPLETED 后 48h 内（或 DELIVERED 期间）发起投诉 |

### 4.3 状态迁移表

| # | 当前 | 触发动作 | 操作者 | 目标 | 副作用 |
|---|---|---|---|---|---|
| T1 | — | 发布订单 | 发单人 | PENDING | 写 push 任务、启动召回 |
| T2 | PENDING | 抢单 | 接单人 | IN_PROGRESS | 锁定接单人、写 accepted_at、停止推送、通知发单人 |
| T3 | PENDING | 取消 | 发单人 | CANCELLED | 停止推送、释放召回队列 |
| T4 | PENDING | 到期（deadline） | 系统 | EXPIRED | 关闭大厅展示、通知发单人 |
| T5 | IN_PROGRESS | 更新进度（已取件 / 配送中） | 接单人 | IN_PROGRESS | 追加 progress 事件、推送发单人 |
| T6 | IN_PROGRESS | 标记送达 | 接单人 | DELIVERED | 写 delivered_at、启动 24h 自动确认定时器 |
| T7 | IN_PROGRESS | 申请取消 | 接单人 | IN_PROGRESS | 生成取消申请，等发单人同意 |
| T8 | IN_PROGRESS | 同意取消 | 发单人 | CANCELLED | 接单人信誉 −3、记录 |
| T9 | DELIVERED | 确认收货 | 发单人 | COMPLETED | 写 completed_at、开放评价、结算 |
| T10 | DELIVERED | 超时未确认（24h） | 系统 | COMPLETED | 同上，标记 `auto_confirmed = true` |
| T11 | DELIVERED | 发起投诉 | 任一方 | DISPUTED | 冻结结算、通知管理员 |
| T12 | COMPLETED | 48h 内投诉 | 任一方 | DISPUTED | 冻结评价展示、进入仲裁 |
| T13 | DISPUTED | 仲裁：支持发单人 | 管理员 | CANCELLED | 接单人信誉扣分、订单不计入统计 |
| T14 | DISPUTED | 仲裁：支持接单人 | 管理员 | COMPLETED | 恢复结算、解除冻结 |
| T15 | COMPLETED | 双向评价 | 双方 | COMPLETED | 写 reviews、更新信誉分 |

**并发约束**：T2 必须原子（见 9.3），T7→T8 与 T9 互斥，T11 与 T9 互斥（先到先得）。

### 5.3 AI 智能推送（FR-PUSH）—— 系统核心

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-PUSH-01 | 空间召回 | P0 | 按召回键查附近在线接单人，默认半径 1000m，返回候选集 |
| FR-PUSH-02 | 多因子排序 | P0 | 距离衰减 + 顺路度 + 信誉 + 活跃度 + 负载惩罚（公式见 9.1） |
| FR-PUSH-03 | Top-N 定向推送 | P0 | 每轮只推给排序前 20 人，避免全校轰炸 |
| FR-PUSH-04 | 阶梯扩圈 | P0 | 5 分钟无人接单 → 半径 ×2（上限 3000m），排除已推人群；15 分钟 → 全量大厅降权展示 + 建议加价 |
| FR-PUSH-05 | 推送频控 | P0 | 单用户每 10 分钟最多 3 条推送、每小时 10 条；超出自动降级为「大厅可见」不推送 |
| FR-PUSH-06 | 多通道触达 | P0 | 站内消息（必达，红点）+ 小程序订阅消息（增强，受微信一次性订阅限制）；Web 端站内消息 |
| FR-PUSH-07 | 推送效果回流 | P1 | 记录曝光、点击、抢单，用于调参 |
| FR-PUSH-08 | 冷启动兜底 | P0 | 在线接单人 < 5 时跳过定向推送，全部进大厅并通知「附近有新单」 |

**召回键的选择（重要设计决策）**

原始需求写的是「根据订单目的地位置推送给目的地附近的学生」。这在**代取快递**这一主场景下是对的，但放到全部场景会失效，原因是两类任务的 POI 分布特征相反：

| 任务类型 | 起点分布 | 终点分布 | 召回键 | 理由 |
|---|---|---|---|---|
| 代取快递 | 高度集中（全校 2～3 个驿站） | 分散（几十栋宿舍楼） | **终点（目的地）** | 终点能形成有效人群分群；接单人多住在目的地附近，取件后顺路带回 |
| 代买 | 分散（食堂/超市/打印店） | 分散 | **起点** | 接单人必须先到购买点，起点才代表可达成本 |
| 代送 | 分散 | 分散 | **起点** | 同上 |
| 其他 | 不定 | 不定 | 起点 + 终点双键取并集 | 兜底 |

实现上统一为「双键召回 + 加权」，召回键由任务类型决定主次：`主键半径 1000m`，`次键半径 1500m`，两集合去重后进入排序。这样既满足原始需求（代取快递按目的地推），又不会在代买场景下推给「目的地附近但离超市三公里」的人。

| FR-ADMIN-05 | POI 字典维护 | P0 | 增删改 POI、批量导入（Excel）、上下架 |
| FR-ADMIN-06 | 参数配置 | P1 | 推送半径、Top-N、在途上限、自动确认时长、信誉规则权重（不重启生效） |
| FR-ADMIN-07 | 操作审计 | P0 | 所有管理动作写 `admin_audit_logs`（谁、何时、对什么、做了什么、前后值） |
| FR-ADMIN-08 | 内容安全 | P1 | 订单描述与评价接入文本安全检测，命中敏感词转人工 |

### 5.10 纠纷处理流程（FR-DISPUTE）

```
发起（任一方，DELIVERED 或 COMPLETED 后 48h 内）
  → 选择原因（未送达/物品损坏/物品不符/态度恶劣/虚假送达）
  → 上传举证（≤5 图 + ≤300 字）
  → 系统冻结：结算、评价展示、信誉变动
  → 被投诉方 24h 内申诉举证
  → 管理员仲裁（48h 内出结果）
       ├─ 支持发单人：订单转 CANCELLED，接单人信誉 −5，计入违规
       ├─ 支持接单人：恢复 COMPLETED，解除冻结
       └─ 双方有责：标记 `partial`，各扣 2 分
  → 结果通知双方 → 允许申诉 1 次 → 终审
```

规则约束：同一订单仅一次纠纷；恶意投诉（成立率 < 20% 且累计 ≥ 3 次）者限制投诉权限 30 天。

## 9. 核心算法与时间复杂度

### 9.1 推送打分模型

候选集 C（召回后），对每个候选 $r$ 计算：

```
S(r) = 0.45 * D(r) + 0.20 * R(r) + 0.15 * C(r) + 0.10 * A(r) + 0.10 * N
D(r) = exp(-dist(r, key) / d0)              # 距离衰减，d0 = 500m
R(r) = exp(-route_gap(r) / 800)             # 顺路度：在途任务终点→本单起点距离
C(r) = (credit - 80) / 40                   # 信誉归一化，裁剪到 [0,1]
A(r) = min(active_7d / 10, 1)               # 近 7 日接单活跃度
N = 随机扰动（0~1），防马太效应，占比 10%
负载惩罚：load >= 3 → 直接剔除；load == 2 → S *= 0.6
```

调参落库到配置表，支持灰度对比（A/B 两组权重）。

### 9.2 复杂度分析

| 环节 | 方案 | 复杂度 | 量级估算（5000 注册 / 800 在线） |
|---|---|---|---|
| 召回附近接单人 | Redis `GEOSEARCH BYRADIUS`（ZSET 跳表） | **O(log N + M)** | N=800，M≈60（1km 内）→ <1ms |
| 召回附近订单（大厅） | Redis GEO + 游标分页 | **O(log N + K + page)** | <2ms |
| 候选过滤（在线/认证/在途/频控） | Pipeline 批量取 Hash / Set | **O(M)** | 60 次读，Pipeline 一次 RTT |
| 打分与排序 | 全排序 O(M log M)；Top-N 用堆 **O(M log N)** | O(M log N) | 60 × log20 ≈ 260 次比较 |
| 推送写入 | 批量 INSERT push_logs + 站内信 | **O(N_push)** | 20 条 |
| 抢单 | Redis Lua 原子 + DB 乐观锁 | **O(1)** | — |
| 订单列表 | 联合索引 + 游标分页（禁 OFFSET） | **O(log N + page)** | — |
| 在途数校验 | Redis Set SCARD | **O(1)** | — |
| 过期扫描 | 定时任务 + 部分索引 `(deadline) WHERE status='PENDING'` | **O(log N + k)** | 每分钟一次 |

**结论**：单次推送端到端 `O(log N + M log N + N_push)`，在 800 在线接单人的量级下总耗时 < 20ms（不含网络写入），完全满足需求中「时间复杂度合理」的约束；且该复杂度随用户数呈对数增长，扩到万级仍然可用。

**禁止事项**：`SELECT * FROM orders WHERE ST_DWithin(...) ORDER BY RANDOM()`、`OFFSET 10000` 深分页、全表 `LIKE '%关键词%'`、逐单循环查用户——这四类写法是校园项目最常见的性能塌方点。

### 9.3 抢单原子性（防一单多接）

三道闸，缺一不可：

1. **Redis Lua（第一道，挡掉 99% 并发）**
```lua
-- KEYS[1]=order:lock:{id}  KEYS[2]=runner:load:{uid}
-- ARGV[1]=uid  ARGV[2]=max_load
if redis.call('EXISTS', KEYS[1]) == 1 then return 0 end
local load = tonumber(redis.call('GET', KEYS[2]) or '0')
if load >= tonumber(ARGV[2]) then return -1 end
redis.call('SET', KEYS[1], ARGV[1], 'EX', 30, 'NX')
redis.call('INCR', KEYS[2])
return 1
```
2. **DB 乐观锁（第二道，保证最终一致）**
```sql
UPDATE orders
   SET status='IN_PROGRESS', runner_id=:uid, accepted_at=now(), version=version+1
 WHERE id=:id AND status='PENDING' AND version=:version;
-- rows_affected = 1 才算成功，否则回滚 Redis 并返回 40901
```
3. **幂等键（第三道，挡重复提交）**：`Idempotency-Key` 存 Redis 24h，重复请求直接返回首次结果。

失败必须**补偿 Redis**（删除锁、DECR 负载），用 try/finally 或事务性消息保证。

## 14. 验收标准（Definition of Done）

**功能闭环**
1. 未认证用户无法发单/抢单，接口层与 UI 层双重拦截。
2. 完整走通：发单 → 被推送到附近 20 人 → 抢单 → 取件 → 送达 → 确认 → 双向评价 → 信誉分变化。
3. 状态机 15 条迁移（T1–T15）全部有自动化测试，非法迁移返回 4xx。
4. 纠纷：发起 → 冻结 → 举证 → 仲裁 → 结果通知 → 申诉，全流程可走通，审计日志可查。

**性能与并发**
5. 100 并发抢同一单，DB 中恰好 1 条 `IN_PROGRESS`，其余返回 40901。
6. 800 在线接单人下，推送召回 + 打分 P95 < 50ms，发单到触达 < 5s。
7. 大厅列表 P95 < 300ms，翻到第 500 条无性能衰减（游标分页验证）。

**双端一致**
8. Web 与小程序在「发单/抢单/进度/确认/评价」五个动作上行为一致，字段级对齐。

**治理**
9. 后台可检索任意订单、封禁用户、仲裁纠纷，所有动作留痕。
10. 敏感信息（手机号、学号）在接口响应中脱敏，抓包验证。

| **A. 线下结算（推荐 MVP）** | 平台只记录金额，双方微信/支付宝自行转账 | 零支付合规风险，最快上线，与个人主体小程序类目兼容 | 赖账无强制力，靠信誉体系约束 |
| B. 平台代收 | 微信支付下单托管，完成后 T+1 结算给接单人 | 闭环完整，纠纷可强制退款 | 需企业商户号、资金池合规、提现与对账，工作量 ≈ 整体 +40% |
| C. 校园卡 | 对接一卡通 | 最合规 | 学校无对外接口，现实不可行 |

**我的建议：M1–M4 走 A，把信誉体系做扎实；拿到商户号后再上 B。**

### 16.2 技术栈是否复用现有脚手架

复用 `FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL + Redis + Celery` 可省 30% 工期（认证、迁移、容器编排都是现成的）。若为课程作业需从零，则按本文档从 M1 起。

### 16.3 小程序方案

| 方案 | 说明 | 适合 |
|---|---|---|
| Taro 3（React） | 复用现有 React 心智与逻辑层，UI 分叉 | 已有 React 代码，推荐 |
| uni-app（Vue） | 生态成熟、社区方案多 | 团队熟 Vue |
| 原生小程序 | 性能与 API 最全 | 只做小程序、不做 Web |

### 16.4 认证方式优先级

若学校邮箱可收外部邮件 → 走 A（邮箱验证码）为主，OCR 兜底；若不可 → 只能 OCR + 人工审核，需预留运营人力（首月约 50～100 单/天审核量）。
