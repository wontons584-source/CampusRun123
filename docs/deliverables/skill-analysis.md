# 技能分析：如何用 AI 从零复现一个 CampusRun

> 用途：课程第 7 项交付 —— 把开发过程做成**别人照着能重现**的 PPT。
> 定位：这份不是"我用 AI 写了个项目"的感想，是一份**操作手册**。看完它，一个没写过这个项目的人应该能自己搭出一个同构的系统。
> 页数：20 页。每页格式统一：**要点 / 配图建议 / 演讲备注**。三段 prompt 是脱敏后的真实版本，可直接复制。
> **配套文件**：三段 prompt 已单独抽成 `appendix-prompts.md`（含逐条解释、验收要点、常见翻车），现场演示"照着能复现"时用附录，PPT 正文只留精简版。

**全篇统一的数字口径**：**707 passed = 615 单元 + 92 集成**（**截至 10 月 29 日**，集成测试跑在真实 PostgreSQL 16.15 + Redis 7 上）· 14 张表 / 27 条索引 · 17 条迁移 / **19 个动作** · 22 次提交 · 列宽事故为 **3 处致命缺陷**（排查时统一放宽了 10 个枚举列）。全文只允许出现 707 与「615 + 92」，不写第二个版本的数字。

**一句话结论（放在封面下方）**
AI 能把"写代码"这件事的耗时压缩一半，但它会把"验证"这件事的难度放大一倍。省下来的时间必须投到验证上，不然是净亏。

## 第 2 页 · 这份分享解决什么问题

**标题**：不是"要不要用 AI"，是"用了以后哪些事变了"

- 变了的事
  - 写代码从"敲"变成"审"——**阅读量的占比从 30% 涨到 70%**
  - 试错成本极低，所以你更容易一次改 5 个地方，然后全乱
  - 它写测试比人快，所以你会**误以为测试覆盖度提高了**
- 没变的事
  - 需求边界不清 → 还是要返工
  - 边界条件没想明白 → 它会给你一个"看起来对"的实现
  - 真实环境的约束（列宽、事务隔离、锁）→ 它不会替你想
- 所以这份分享的核心主张
  - **把 AI 当"实现者"，不要当"验收者"**
  - 验收标准必须由人写，且必须是能跑、能红、能绿的断言

**配图建议**：左右对照表（变了 / 没变），两列等宽。

**演讲备注（约 40 秒）**
我的核心主张就一句：把 AI 当实现者，不要当验收者。它非常适合"我已经想清楚了，你帮我写出来"；它非常不适合"你看看这样行不行"。因为它回答"行不行"的时候，用的是它自己造的那个替身。

## 第 3 页 · 全流程地图（6 个阶段）

**标题**：从一句话需求到一个能跑的系统，我拆成 6 步

| 阶段 | 产出 | 关键动作 | 验收方式 |
|---|---|---|---|
| ① 需求 | PRD（行为 + 规则 + 状态迁移表） | 让 AI 做"提问者"，不急着让它写方案 | 每条需求都能对应一个状态或一个守卫 |
| ② 架构 | ADR + 数据模型 + 索引清单 + 任务分解 | 强制它写"为什么不用 X" | 每条索引能说出服务哪个查询 |
| ③ 骨架 | 目录、迁移、配置、错误码、响应信封 | 一次只搭一层，搭完立刻能跑 | `alembic upgrade head` 成功 |
| ④ 编码 | 状态机、守卫、仓储、接口 | 一个任务一个提交 | 每个提交都能独立回退 |
| ⑤ 验证 | 单测 + 真库集成 + 并发判据 | **在真实 PG / Redis 上重跑每一个结论** | 断言可判定，不写"应该正确" |
| ⑥ 收口 | 文档回写、删掉过期内容 | 代码改了文档必须跟着改 | 文档里的数字与仓库一致 |

- 最容易跳步的是 ⑥。我跳过，代价是后来有 4 处文档和实现对不上，回查花了一个晚上

**配图建议**：横向流程条，6 个方块，每个方块下面标"产出物"；⑥ 用虚线框，标"最容易跳过"。

**演讲备注（约 30 秒）**
六步里，⑤ 和 ⑥ 是大部分人（包括我）最容易糊弄的。⑤ 我有一次糊弄了，第 12 页讲代价。⑥ 我直接跳过了，结果四处文档和实现对不上，回查花了一个晚上。

## 第 4 页 · 角色分工

**标题**：谁负责什么，边界要写死

| 我负责（不可外包） | AI 负责（可以放心交） |
|---|---|
| 判定"什么算对"（判据、断言） | 按判据写出实现 |
| 边界条件的枚举（0 秒 / 45 分 / 45 分零 1 秒） | 把边界写成参数化测试 |
| 真实环境的约束（列宽、隔离级别、锁） | 把约束翻译成 SQL / 迁移 |
| 数据模型与索引的取舍 | 生成迁移脚本与索引 DDL |
| 最后的验收签字 | 自查、补充遗漏分支、写注释 |

- 一条硬规矩：**AI 说"已通过"不构成验收，我只认我自己跑出来的结果**
- 一条软规矩：让它解释"为什么这么写"，比让它"再检查一遍"有用得多

**配图建议**：左右两栏，中间一条竖线，竖线顶端标"判据在这里产生"。

**演讲备注（约 35 秒）**
左边这一列我做了个标记叫"不可外包"。特别是第一行：判定什么算对。这件事如果你交给 AI，它就既当运动员又当裁判，第 12 页那次事故就是这么发生的。

## 第 5 页 · 阶段① 需求：让 AI 当提问者

**标题**：不要一上来就让它写方案

- 错误开场：「帮我设计一个校园跑腿系统」→ 得到一份任何项目都能套用的方案
- 正确开场：**先让它问你问题**
- 关键动作：把"异常路径"单独列成一章
  - 顺利路径（发单→抢单→送达→确认）：2 小时能写完
  - 异常路径（超时、失联、取消、争议、仲裁）：占了我一半以上的设计时间
- 需求阶段必须产出的一张表：**状态迁移表**
  - 每行：从哪个状态 / 什么动作 / 到什么状态 / 谁可以做 / 什么条件 / 触发什么副作用
  - 这张表是后面写代码和写测试的**唯一来源**

**配图建议**：左边放"错误开场 → 泛泛方案"的对比，右边放状态迁移表的局部（3 行），用高亮标出"谁可以做 / 什么条件"两列。

**演讲备注（约 40 秒）**
很多人用 AI 做需求会得到一个特别漂亮的方案，漂亮到换个项目名也能用。因为你的输入太宽了。
我的做法是先让它当提问者：你把要问我的问题列出来，我一个一个答。它问的问题里有一半是废话，但剩下那一半会逼我想清楚一些我原来没想的事，比如"接单人能不能同时接多单"。
另外我把异常路径单独列了一章。这一章占了设计时间的一多半，但它是这个项目真正的价值所在。

## 第 6 页 · 阶段② 架构：三段真实 Prompt 之一（架构设计）

**标题**：Prompt 1 · 让 AI 做架构设计

```
【背景】
单人开发，工期紧（周末两天做后端内核）。技术栈锁定：
Python 3.11 + FastAPI + SQLAlchemy 2.0(async) + PostgreSQL 16 + Redis 7。

【任务】
为"校园跑腿"的订单系统做架构设计。请只输出以下 5 项，不要写代码：
1. 模块划分（每个模块一句话职责 + 边界，说明哪些是纯函数、哪些碰 IO）
2. 核心表的 DDL 要点（字段、类型、必须的约束）
3. 索引清单：每条索引必须写明"服务哪个查询"，写不出查询的索引不要列
4. 关键流程的并发分析：列出所有"两个请求同时到达会出错"的位置，
   每个位置说明用什么机制保证（DB 约束 / 行锁 / 乐观锁 / 分布式锁），
   并说明为什么不用其他机制
5. 明确的"不做"清单：本次不做什么，以及如果不做会有什么后果

【约束】
- 不要引入消息队列、不要微服务、不要 CQRS（一个人维护不了）
- 每个设计决定必须给出"为什么不用另一个方案"的一句话理由
- 如果某项信息不足以做决定，列到"待确认"里，不要自己假设

【格式】
表格优先，每个判断后面不要写"最佳实践"，要写"因为……所以……"。
```

**要点**

- 四条设计约束决定了输出质量：**"5 项、不要代码"**（防跑题）、**"写明服务哪个查询"**（防堆索引）、**"为什么不用另一个"**（防套话）、**"信息不足列到待确认"**（防编造）
- 实际效果：一次输出里有 3 处"待确认"是我确实没想过的（在途单上限、Redis 与 DB 谁是权威、争议恢复后超时怎么算）

**配图建议**：prompt 全文放左半页（小字号、等宽字体），右侧用三个箭头标出四条约束分别防什么。

**演讲备注（约 50 秒）**
这条 prompt 里真正起作用的是四个"防"。
第一，"只输出 5 项，不要写代码"。不加这句，它会直接开始写代码，架构部分就跳过了。
第二，"每条索引必须写明服务哪个查询"。因为 AI 特别喜欢给你建一堆索引显得很专业。加了这句以后，它列出来的每一条我都能拿去核对。
第三，"每个设计决定必须给出为什么不用另一个方案"。这是防套话最有效的一句，因为它必须把被否掉的方案说出来。
第四，"信息不足就列到待确认，不要自己假设"。这一条救了我，它列了三项我确实没想过的事，其中一项就是"在途单上限"——一个人最多同时接几单。

## 第 7 页 · 阶段③ 骨架：一次只搭一层

**标题**：让项目尽早"能跑起来"，哪怕它什么都不做

- 顺序（每一层搭完都必须能跑通）
  1. 目录 + 配置 + 日志 + 依赖注入 → 一个 `/health` 能返回
  2. 数据模型 + 初始迁移 + 配置种子 → `alembic upgrade head` 成功
  3. 错误码 + 统一响应信封 + 异常处理器 → 一个故意的错误能返回正确结构
  4. 游标分页 + 可注入时钟 + trace_id → 这两个是"以后所有代码都要用"的地基
- 为什么顺序不能换
  - 错误码和响应信封晚做，后面每个接口都要回头改
  - 时钟注入晚做，所有超时逻辑都没法测
- 这一阶段的判据
  - 一次迁移能从空库跑到 head，再从 head 降回 base，**来回都要能跑**
  - 故意抛一个业务异常，客户端拿到的 JSON 结构符合统一信封

**配图建议**：四层堆叠图，右侧标"每层完成后立刻验证什么"；第 4 层加一个红色感叹号标"最容易被推迟，代价最大"。

**演讲备注（约 35 秒）**
第 4 层我想强调一下：错误码、响应信封、游标分页、可注入时钟。这四样东西是地基，不是功能。
它们最容易被推迟，因为它们不像功能那样能立刻展示。但错误码晚做，后面每个接口都要回头改；时钟注入晚做，我所有关于 45 分钟的测试都写不出来，因为测试没法让系统认为现在是 45 分钟以后。

## 第 8 页 · 阶段④ 编码：三段真实 Prompt 之二（状态机守卫）

**标题**：Prompt 2 · 让 AI 写最容易写错的那部分

```
【任务】
实现订单状态机的守卫函数。守卫必须是纯函数：
签名 (order, actor, payload, cfg) -> bool，不碰数据库、不碰网络、不读全局时钟。
数据不够就抛业务异常，不要返回 False 含糊过去。

【唯一事实来源】
状态迁移表见附表（17 行）。你必须逐行实现，编号对齐，不许合并、不许新增。

【本次只做这两个守卫，都是"发单人"才能触发的零人工出口】
A. 无责取消（迁移 T17）：进入"已取消"，扣接单人 3 分
   条件：订单当前"进行中" AND 操作者=发单人
         AND 接单人从未产生过任何进度
         AND 现在距"被抢单时刻" >= 45 分钟
B. 失联投诉（迁移 T16）：进入"争议"并冻结
   条件：订单当前"进行中" AND 操作者=发单人
         AND 接单人已产生过进度
         AND 现在距"最后一条接单人进度" >= 45 分钟

【术语定义（必须严格遵守，不许在别处重新定义）】
「接单人进度」= 动作 ∈ {已取件, 在路上, 已送达, 备注} 且 操作者 id = 接单人 id。
注意：发单人的催单/备注/申请取消 都不算进度。
原因：如果把发单人的催单也算进度，则发单人第 10 分钟催一次，
      条件 A 的"从未有进度"永久不成立，而条件 B 的静默计时刚被重置还要再等 35 分钟，
      两条出口同时不可走 —— 这比原 bug 更糟。

【边界必须显式处理】
- 恰好 45 分 00 秒 → 允许
- 44 分 59 秒 → 拒绝，错误码 42201，文案必须说明还差多少
- 从未被抢单 / 已在终态 → 拒绝，错误码必须是具体的那个，不要笼统 400

【输出】
1. 两个守卫函数（含类型标注）
2. 参数化测试：正常 / 边界下 1 秒 / 边界 / 边界上 1 秒 / 角色不对 / 状态不对，各一条
3. 一段 100 字以内的注释，说明"为什么进度定义要限制 actor_id"
```

**要点**

- 五个约束各自的作用
  - **纯函数** → 才能穷举测试（不用起数据库）
  - **唯一事实来源 + 逐行对齐** → 防它顺手"优化"掉一条迁移
  - **术语定义 + 给出反例的原因** → 这是最关键的一段，把"为什么不能那样"写进 prompt，它才不会换个地方重新定义
  - **边界显式列出** → 不给边界，它只测 45 分钟那一秒
  - **要求输出注释** → 注释是给三个月后的自己看的，也是给 review 用的

**配图建议**：prompt 分段上色（任务 / 事实来源 / 术语定义 / 边界 / 输出），右侧竖排标注"每个约束防的是什么"。

**演讲备注（约 55 秒）**
这条 prompt 里我最想让大家记住的是"术语定义"那一段，尤其是括号里的那句原因。
我第一版没有写那段原因，只写了"进度=接单人的动作"。结果它实现的时候，在另一个地方把所有动作都算进去了，因为它觉得"备注也是动作啊"。
后来我学到一个办法：**不只告诉它定义是什么，还要告诉它如果理解错了会发生什么**。因为 AI 补全的时候特别喜欢自洽——你不给它一个明确的理由，它就会用自己的一套逻辑填上空白。
第三条也是同一个道理。我明确写了"恰好 45 分允许，44 分 59 秒拒绝"，它才会把边界当成一个需要处理的点，而不是一个数字。

## 第 9 页 · 阶段⑤ 验证：为什么"AI 自己验证自己"不可靠

**标题**：它会给你发一张合格证，签发人也是它

- 它的三种"通过"分别意味着什么

| 它说 | 实际含义 | 可信度 |
|---|---|---|
| "测试全部通过" | 它写的测试通过了 | 低——它写测试时会**绕过它实现不了的东西** |
| "已处理边界情况" | 它想到了 45 分钟 | 中——但没想到 44 分 59 秒和从未被抢单 |
| "符合最佳实践" | 它训练数据里有类似代码 | 很低——这类话没有任何信息量 |

- 结构性原因（不是它"不努力"）
  - 它验证的是**代码的自洽性**，不是**环境的约束**
  - 它会用替身（内存仓储 / mock）绕过真实依赖，而 bug 常常藏在被绕过的那个地方
  - 它没有"我记得这一列多宽"这种记忆——列宽这种东西，它写完就不看了
- 应对：把验证拆成"它能做的"和"只有人能做的"

| AI 可以做 | 只能人做 |
|---|---|
| 生成测试用例清单 | 决定哪些用例**必须**存在于真实环境 |
| 参数化边界值 | 指出还有哪些边界没被想到 |
| 跑测试并汇报 | 判断"这次全绿"是否可信 |

**配图建议**：三种"通过"做成三张卡片，每张打一个可信度分数（用点阵，不要用星星）；下方左右分栏。

**演讲备注（约 45 秒）**
为什么它验证自己不可靠？我想说清楚这不是它偷懒。
它验证的是代码自己的自洽性——逻辑通不通。但 bug 常常藏在环境的约束里，比如一个字段装不下九個字母。这一类事它不会主动去看，因为它的注意力在你的要求上，不在数据库上。
而且它验证的时候会用替身。用内存仓储代替数据库，这在单测里是对的，但如果你只跑单测，你验证的就是"替身里的逻辑对不对"。
所以我把验证拆成两半：它能做的，和只有人能做的。右边这一列只有三条，但它是全部价值的所在。

## 第 10 页 · 真实案例复盘：三个事故，都是全绿之后才发现的

**标题**：三个 bug 都不在函数里，在函数与函数之间

| # | 案例 | 症状 | 为什么测试没抓到 |
|:---:|---|---|---|
| 1 | 列宽太窄 | 真库 `INSERT` 直接报错 | 内存替身不校验列宽 |
| 2 | 在途上限失效 | 已有 3 单还能抢第 4 单 | 测试手填上下文对象，没走真实 SQL |
| 3 | 发单不落库 | 接口 201，刷新后数据消失 | 测试绕过 HTTP 层，测不到事务边界 |

> **三个 bug 有一个共同点：它们都不在函数内部，而在函数与函数之间。**
> 单元测试擅长验证「这个函数算得对不对」，天生测不到「这条链路接没接上」。

### 案例 1 的完整时间线（复盘的写法示范）

```
① 写模型：文档里枚举值写成 UNSETTLED / PUBLISHER / EXCELLENT
        ↓  AI 生成 DDL 时统一给了 varchar(8)
② 写单测：当时全部通过（现全量 707 = 615 单元 + 92 集成，截至 10/29）
        因为用了内存替身仓储，它不校验列宽
        ↓  AI 汇报"测试全部通过"
③ 我以为可以接真库了
        ↓
④ 第一个发单请求 → 报错
       三条同时失败（3 处致命缺陷）：
         settle_state      DEFAULT 值是 UNSETTLED(9) → 任何插入都失败
         actor_role        PUBLISHER(9)             → 发单人进度全写不进
         credit_level      EXCELLENT(9)             → 生成列，分数≥110 的用户插不进
        ↓
⑤ 修复：把 10 个枚举列统一放宽到 varchar(16)（3 处已经炸了，另外 7 处余量不够），
        然后加一个 370 行的自检文件（这才是真正的修复）
```

### 案例 3 的三行要点（最贴近真实工程的一个）

```
① 依赖里只 close() 从不 commit()；service 层按约定也不提交
        ↓  两边都不提交
② 每条 HTTP 请求的数据凭空消失：201、订单号、页面跳转全都正常，刷新即空
        ↓  为什么抓不到：测试直接调 service，session 由 fixture 管，
           断言在同一个未提交的事务里做 → 永远看得到"数据还在"
③ 修复：yield 之后 commit()，异常 rollback() 再 raise
        ↓  验证方式：请求结束之后**另开一个连接**查库，而不是复用测试会话
```

**为什么 370 行的列宽自检救不了案例 3**：它是纯模型层断言，不碰事务。**纯函数层的护栏再厚，也拦不住"根本没提交"这件事。**

**配图建议**：上半页放三案例表格（第 3 行加红框）；下半页左放案例 1 时间线、右放案例 3 的三行要点；底部那句总结用大字号横贯。

**演讲备注（约 60 秒）**
这条时间线是案例 1，我把它当"怎么复盘"的写法示范：写清每一步、写清当时的判断、写清为什么这个判断是错的。
案例 3 我不画时间线了，因为它只有三行：依赖只关闭不提交，service 也按约定不提交，于是每条请求的数据都消失。接口返回 201，订单号都生成了，刷新一下没了。
我想强调的是最后一句话：三个 bug 都不在函数内部，都在函数之间。第一个是"代码与数据库之间"，第二个是"两次 SQL 之间"，第三个是"请求与事务之间"。
而这三处，恰好都是单元测试的盲区——因为它天然会绕开这些边界。

## 第 11 页 · 三段真实 Prompt 之三：如何让它抓自己的 bug

**标题**：Prompt 3 · 不要问"还有问题吗"，要给它一个能失败的判据

```
【任务】
我现在怀疑"枚举列宽不足"这类问题还会复发。请你设计一个**纯模型层**的
测试文件，不依赖数据库、每次 pytest 都会跑，用来把这类问题钉死。

【必须覆盖的 5 条断言】
1. 每个枚举列：该列所有允许取值的最长长度 <= 列声明的长度
2. 每一列 String 类型：必须被登记为"枚举列"或"自由文本列"，
   漏登记直接失败（这是防止新增列时遗忘的闸门）
3. 登记表里的每个键，必须真实存在于模型定义中（防改名后失配）
4. 登记表里的枚举值，必须和生成列的 SQL 表达式文本一致
   （防"登记表自己写错、测试跟着错"）
5. 把当前各列的剩余宽度钉成快照：新枚举值吃掉余量时失败并提示"该加宽了"

【硬约束】
- 不许 connect 数据库、不许 mock 数据库、不许读迁移文件
- 只允许 import app.models
- 每条断言失败时，报错信息必须包含：列名 / 当前宽度 / 最长取值 / 差多少

【验收】
请你先故意把某一列宽度改小 1，跑一次给我看它必须失败；
再改回来，跑一次给我看它必须通过。两个结果都要贴出来。
```

**要点**

- 关键在最后一段：**要求它先造一个失败**
  - 只让它"写测试",它会写一堆必然通过的断言
  - 要求"先红后绿",它才会真的去验证自己的测试有效
- 第 2 条断言是整个文件的核心
  - 前 1/3/4/5 条都是修当下，只有第 2 条是**防未来**——它让"新增列"这个动作必须先过一道闸
- 实际产出：370 行，覆盖 14 张表所有 String 列
  - 它拦的不是"未来的某个 bug"，是"下一次遗忘"——新增一列不登记，测试直接跑不过

**配图建议**：prompt 中"验收"段单独高亮；右侧放"先红后绿"的两张 pytest 输出对比（FAILED / PASSED）。

**演讲备注（约 50 秒）**
这条 prompt 最重要的不是那五条断言，是最后那一段：我要它先给我看它失败的样子的。
因为我发现，你让 AI 写测试，它会写一堆必然能通过的断言。你跑一下，全绿，你就信了。但它可能根本没测到你担心的事。
要求它先故意改坏一个值，跑一次必须失败，再改回来必须通过——这一步会逼它自己验证自己的测试真的有效。这个技巧我后来用在所有它写的测试上。
第二条断言我也想单独说一下。前面几条都是在修当下，只有第二条是防未来：新增一个字符串列，必须在登记表里登记，不登记就跑不过。这是闸门，不是补丁。

## 第 12 页 · 三个关键技巧（总览）

| 技巧 | 一句话 | 什么时候用 | 成本 |

## 第 13 页 · 技巧深挖 ①：可验证护栏

**标题**：把"应该"换成"等于"

- 同一个需求，三种写法

| 写法 | 例子 | 能不能验收 |
|---|---|---|
| 愿望 | 抢单要防止并发 | 不能 |
| 标准 | 抢单时只能有一个人成功 | 勉强，靠人判断 |
| 判据 | 100 并发后 `count(*) where status='IN_PROGRESS'` == 1，其余 99 个返回 40901 | 能，能红能绿 |

- 三道护栏，各管一段
  - **数据库层**：唯一约束 + 部分索引 → 脏数据根本插不进去
  - **状态机层**：状态 × 动作矩阵穷举 → 非法迁移必须抛特定码
  - **接口层**：错误码契约 → 拒绝时返回的必须是"具体那个码"，不是笼统 400
- 为什么护栏比文档重要：文档会过期，护栏会让代码跑不过

**配图建议**：三种写法做成三档阶梯，第三档用绿框；下方三道护栏做成三条横杠。

**演讲备注（约 35 秒）**
中间这一档"标准"看起来已经很具体了，但它还是要靠人来判断。判据的好处是它可以交给机器。
我还要说一句为什么护栏比文档重要。文档会过期，我自己就有四处文档和实现对不上。但护栏不会,它会让代码直接跑不过。所以现在我更愿意花时间写护栏，而不是写文档。

## 第 14 页 · 技巧深挖 ②：为什么必须看真实数据库

**标题**：替身能证明逻辑，证明不了环境

**内存替身会漏掉的五类问题**

| 类别 | 例子 | 单测能抓吗 |
|---|---|---|
| 类型/宽度 | varchar(8) 装 UNSETTLED(9) | 不能 |
| 约束 | 唯一索引冲突、外键顺序 | 不能 |
| 事务与隔离 | CAS 的 rowcount、并发读到的旧值 | 不能 |
| 默认值 / 生成列 | DEFAULT 值本身超宽、生成列表达式 | 不能 |
| SQL 语义 | NULL 比较、时区、`ORDER BY` 稳定性 | 不能 |

- 所以我的分层
  - **单元测试**（占大头）：逻辑、守卫、矩阵、边界 → 快，每次跑
  - **集成测试**（62）：真事务、真并发、真 Lua → 慢，但每个结论都要过一遍
  - **判据式并发测试**：100 并发打一单，断言写死结果
- 一个具体做法：**同一件事在两个层面各写一次**
  - 守卫单测：45 分 00 秒允许 / 44 分 59 秒拒绝（纯函数，秒级）
  - 集成测试：真的造一条 45 分钟前的时间戳，走完整接口（秒级，但过真库真事务）

**配图建议**：五类问题的表格，右侧一列全部打叉——这个视觉冲击比文字强；下方放测试金字塔，但标注"每层的判据是什么"。

**演讲备注（约 40 秒）**
这五类问题有一个共同点：它们都不是"逻辑错"，是"环境不允许"。
而 AI 擅长逻辑，不擅长环境。这不是它的缺陷，是它的信息里没有你这台数据库。
所以我的做法是同一件事在两层各写一次。守卫那一层管边界值对不对，集成那一层管真的事务里会不会炸。这两层只要有一层红，我就不往下走。

## 第 15 页 · 技巧深挖 ③：用标签做回退点

**标题**：一个人开发，最怕"改着改着不知道哪一步坏了"

- 提交粒度：**一个任务一个提交，一个提交只做一件事**
  - 22 次提交的实际分布：`feat` 7 · `docs` 6 · `test` 4 · `chore` 3 · `fix` 2
  - 这 4 次 `test` 里有 3 次紧跟在对应 `feat` 后面（仓储 → 仓储/Lua 原子性、配置加密 → 配置加密校验、发单 → 发单校验），让"功能提交自带验收"这件事成立
- 提交信息用动词开头，写清"做了什么"而不是"改了文件"
  - 好：`fix: 修正 10 个枚举列宽不足导致的写入失败`
  - 差：`修改 model 文件`
- 打标签的时机（三条硬规则）
  1. 一次迁移能从空库跑到 head 并降回 base → 打
  2. 状态机 17 条迁移全部实现且矩阵测试通过 → 打
  3. 一组集成测试在真库上稳定通过两次 → 打
- 回退的正确姿势
  - 出问题时**整体退回上一个标签**，不要在泥潭里逐个文件 `git checkout`
  - 因为 AI 改动的关联性很强，你以为只改了 A，它顺手动了 B

**配图建议**：`git log --oneline --graph` 的截图（真图，22 条），用色块标出 `feat:` / `test:` / `fix:` 三类；右侧列三条打标签规则。

**演讲备注（约 35 秒）**
我特意让 feat 和 test 交替出现，就是让每个功能提交都自带它的验收。这样任何一个标签点退回去，都是一个"功能完整 + 测试通过"的状态。
还有一条踩出来的经验：AI 改动的关联性特别强。你让它改一个列宽，它可能顺手把一个相关的模型定义也重排了。所以出问题的时候不要逐个文件去看，直接整体退回上一个标签，重来一次，比在泥潭里修快得多。

## 第 19 页 · 时间与成本估算

| 需求 + 架构（文档） | 约 1.5 天 | 1 天 | 文档不用写到 7 万字 |
| 骨架 + 数据模型 | 约 1 天 | 0.5 天 | 会用 Prompt 3 从第一天就卡住列宽 |
| 状态机 + 守卫 | 约 1 天 | 0.5 天 | 会用 Prompt 2，把术语定义写清楚 |
| 仓储 + 并发 | 约 1.5 天 | 1 天 | 已经知道 advisory lock 的必要性 |
| 验证与返工 | 约 1 天（含列宽事故） | 0.5 天 | 事故成本可以省掉 |
| 文档回写 | 0.5 天 | 0.5 天 | 这部分省不掉，只能提早做 |
| **合计** | 约 6.5 天 | 约 4 天 | |

- 省下来的 2.5 天里，有 1 天是"列宽事故"的直接成本，另外 1.5 天是"术语定义不清"导致的重写
- 结论：**AI 省下的是打字时间，返工时间取决于你写判据的水平**

**配图建议**：两列柱状对比（实际 vs 重来），只标两项差异最大的；不要饼图。

**演讲备注（约 25 秒）**
这张表我算得比较诚实。省下来的时间不是来自"AI 写得更快"，AI 一直很快。省下来的是返工：一天是列宽事故，一天半是术语定义不清导致的重写。这两件事都是我的问题，不是它的问题。

## 第 20 页 · 结语：AI 协作的边界

**标题**：它擅长什么，不擅长什么

| 它很擅长 | 它不擅长 |
|---|---|
| 把已经想清楚的规则翻译成代码 | 判断规则本身对不对 |
| 生成测试用例的**清单** | 判断哪些用例必须跑在真实环境 |
| 在 17 条迁移里保持命名和编号一致 | 发现某一条迁移的**语义**和另一条冲突 |
| 一次性重命名、搬移、格式化 | 判断这次改动会不会破坏别处 |
| 解释一段代码在干什么 | 知道你**为什么**要这段代码 |

- 所以我的分工是固定的：**我出判据，它出实现，环境出裁决**
- 一句留给自己的话
  - 它能把"想清楚的事"写得又快又好
  - 它没办法替你想清楚

**配图建议**：左右两栏对照表，最后一行"我出判据 / 它出实现 / 环境出裁决"做成一条三人接力图（三个小方块）。

**演讲备注（约 30 秒）**
最后这张表我建议大家只记右边那一列，因为左边那一列你用两天就知道了。
它的边界不是能力边界，是信息边界。它不知道你这台数据库的列宽，也不知道你为什么在意那 45 分钟。所以最后一句：它能把想清楚的事写得又快又好，但它没办法替你想清楚。

## 附：三句话总结

1. **判据比需求重要**：能红能绿的断言，胜过十页描述。
2. **环境比测试重要**：替身验证替身，等于没验证。
3. **回退比修复重要**：整体退回上一个标签，比在泥潭里逐个文件修快得多。
