**演讲备注（约 35 秒）**
大家好，我做的东西叫 CampusRun，简单说就是校园里的"代取快递"。名字起得挺大，但功能很朴素：一个人在宿舍躺着，另一个人顺路帮他把快递从菜鸟驿站带到楼下，跑腿的人赚三五块钱。

## 第 2 页 · 我的出发点

**标题**：我为什么做这个，而不是做个更"好看"的项目

- 我不是先有技术再找题目，是先被这件事烦了两年
- 大二一年，我大概有 30 多次请人代取快递，全部发生在微信群里
- 群里的代取：喊一句"有人去菜鸟吗"，然后靠运气、靠人情、靠对方人品
- 丢过件，也见过别人代取拿了钱不送
- 我想做的不是"再做一个微信群"，是把这件事的**责任边界**写清楚

**配图建议**：一张微信群聊天截图（打码），满屏"有人去XX驿站吗"；旁边放一句灰色批注"这不是需求，这是没办法"。

**演讲备注（约 40 秒）**
我一开始想做个更"拿得出手"的题目，比如推荐算法、比如大模型应用。但我后来越想越觉得，那些东西我做完了自己也不会用。
代取快递这件事我是真的被烦了两年。我统计过，大二一年我大概在群里求人带了三十多次快递，其中有两次丢件，一次是对方拿了钱没送，我在群里问了两天，最后也没结果。
所以我的出发点不是"缺一个工具"，而是"缺一套规则"。工具可以随时换，规则得有人先写出来。

## 第 3 页 · 痛点（一）：一个具体的下午

**标题**：一个真实的下午，比十张调研图表有用

- 12:10 下课，下一节课 14:00，中间只有 110 分钟，还要吃饭
- 菜鸟驿站 18:30 关门，晚课到 17:40，走过去刚好关门前三分钟
- 快递柜超过 12 小时开始计时收费，一个件一天 1 块钱——不是大钱，但很烦
- 12:00–12:40 是驿站峰值，取一个件平均排 15 到 20 分钟，两个件可能要排两次
- 结果是：**下午有课的人，注定取不到当天的快递**

**配图建议**：左边课程表截图（用色块标出 8:00–11:40 连续四节），右边驿站排队实拍，中间用一条时间轴把两端连起来。

**演讲备注（约 45 秒）**
我举一个我自己的例子，因为它比任何调研数据都说明问题。
我周三上午是连续四节课，8 点到 11 点 40。驿站 18 点半关门，我下午还有课，5 点 40 下课走过去，正好赶上关门。
那我能去的时间只有 12 点 10 分到 1 点半这一段。但这一段是驿站一天里最挤的时候，取一个件排 15 到 20 分钟，两个件可能还得排两次队，因为货架不一样。
所以对我来说，问题不是"取快递很麻烦"，是"我的课表和我能取快递的时间，在物理上不重叠"。这件事靠"提醒自己早点去"是解决不了的。

## 第 4 页 · 痛点（二）：四类痛点，以及现有办法为什么不行

**标题**：不是"不方便"，是四个具体的断点

**痛点拆解（四格）**

| 断点 | 具体表现 |
|---|---|
| 时间冲突 | 课表连续四节 + 驿站 18:30 关门，可用的窗口只有 110 分钟 |
| 排队成本 | 峰值单件 15–20 分钟，多件要多次排队，成本不可预测 |
| 信息不对称 | 快递到了不一定通知到你；群里喊代取，谁接了、走到哪了，全都不知道 |
| 信任缺失 | 没有凭证。丢件、拿错件、拿了钱不送，双方都拿不出证据 |

**现有三种办法，各差在哪**

- 自己在群里喊：靠人情，靠运气；**没有进度，没有凭证，全靠对方人品**
- 让室友带：只能解决一次，第二次就不好意思开口了
- 自己跑一趟：回到第 3 页那个下午，物理上做不到

**配图建议**：四格痛点用图标 + 短句，不要长段落；下方三行做"办法 → 差在哪"的对照，用红叉标记。

**演讲备注（约 50 秒）**
把这四类拆开看，其实只有一个核心：**没有凭证**。
时间冲突和排队是成本问题，这个没办法，只能转移。但信息不对称和信任缺失，是"没人记账"的问题。
微信群里喊代取，本质上是把一次交易外包给了人情和运气。你没办法知道对方走到哪了，也没办法在出事的时候拿出证据。
所以我后来给这个项目定的第一句话不是"方便"，是"可追溯"。方便是结果，可追溯是前提。

## 第 5 页 · 解决方案：CampusRun 是什么

**标题**：一句话说清楚

> 一个单校区内的跑腿撮合系统：发单人发一单（去哪、取什么、给多少钱），接单人在大厅里抢，全过程留痕、有出口、有惩罚。

**主流程图（横向五步 + 两个旁路）**

```
① 发单            ② 进大厅          ③ 抢单           ④ 履约           ⑤ 确认收货
取件码加密落库  →  按校区/类型筛选 →  CAS 原子抢占  →  已取件/在路上  →  发单人确认
酬劳区间校验                       一人一单唯一                       自动 24h 兜底
                                                                          
旁路 A：45 分钟无进度 → 发单人无责取消         旁路 B：45 分钟静默 → 失联投诉，冻结待裁
```

- 「发单」和「抢单」之间不需要聊天，所有必要信息都在单里
- 「履约」每一步都是一个事件，不是一个状态位——这是后面一切的前提
- 两个旁路是设计里我最在意的部分：**任何一方卡住，都必须有零人工的出口**

**配图建议**：这张图就是核心，横版占满整页，五步用等宽方块，两条旁路用虚线从③/④下方绕回，末端标"惩罚/退款"。

**演讲备注（约 45 秒）**
一句话：发单人发一单，接单人在大厅抢，全过程留痕。
流程有五步，但真正花心思的是底下两条虚线。上面这条路是顺利的情况，顺利的情况其实最好写。难的是"不顺利"：接单人接了单然后人消失了，怎么办？
我在设计的时候给自己定了个规矩：**任何一个角色卡住，都必须有一条不需要客服介入的出路**。所以有了旁路 A 和旁路 B——45 分钟是一个关键数字，下一页会讲为什么是 45。

## 第 6 页 · 三条设计原则

**标题**：三条原则，决定了后面所有技术选型

- **原则一：每一步都是事件，不是一个状态位**
  - 订单不是只有"进行中"，而是有 17 条状态迁移 + 一条按时间排序的进度流
  - 好处：能回答"他上次动是什么时候"，这是所有超时判断的唯一依据
- **原则二：每个卡住的地方都要有出口**
  - 有进度但静默 → 投诉（冻结待裁）；完全没进度 → 无责取消
  - 两条出口互斥且都为零人工，不能靠"找管理员"
- **原则三：权责写进数据库，不写进客服嘴里**
  - 30 多个业务错误码是契约：前端按码分支，不按文案分支
  - 抢单失败有四种都可能是 409，必须能区分"被别人抢了"和"你手上单太多了"

**配图建议**：三列竖排卡片，每列一句原则 + 一行"如果不这么做会怎样"的反例。

**演讲备注（约 40 秒）**
这三条原则是我在写第一行代码之前就定下来的，后面所有的技术选择基本都能回溯到这三条。
第一条最影响架构。如果订单只是一个"进行中"的状态位，那我永远回答不了"接单人多久没动了"这个问题。所以我把每一次操作都记成一条带序号的事件。
第三条是我在写接口的时候被自己烦到才定下来的。抢单失败有四种原因，如果都返回一个 409，前端只能显示"操作失败"，用户不知道该刷新还是该先去把手上那单送完。

## 第 7 页 · 技术架构

**标题**：四层，一个人写也扛得住

```
┌──────────────────────────────────────────────────────────┐
│ 前端      React 18 + Vite + MUI                          │
│           登录 / 大厅列表 / 订单详情（3 页，进行中）        │
├──────────────────────────────────────────────────────────┤
│ API 层    FastAPI · 统一响应信封 · 30+ 业务错误码          │
│           游标分页 · 可注入时钟 · trace_id 全链路           │
├──────────────────────────────────────────────────────────┤
│ 领域层    order    状态机 17 迁移 / 19 动作 / 守卫纯函数    │
│           grab     抢单三道闸 + 补偿                       │
│           config   sys_configs + Redis 快照 60s 热生效     │
│           poi      地点字典（进行中）                      │
├──────────────────────────────────────────────────────────┤
│ 数据层    PostgreSQL 16   14 表 / 27 索引（含 5 条部分索引）│
│                           CAS 乐观锁 · seq 并发分配        │
│           Redis 7         Lua 抢单锁 / 频控 / GEO 心跳     │
└──────────────────────────────────────────────────────────┘
```

- 模块化单体，不是微服务——一个人维护不了三个进程的部署
- 守卫是**纯函数**（入参出参都是普通对象），只为了能被穷举测试
- 时钟可注入：所有和时间有关的判断都不直接调 `now()`，测试才能造出"45 分零 1 秒"这种边界

**配图建议**：就用这张分层图，用不同深浅的底色区分四层；右侧竖排标一行小字"为什么不用微服务"。

**演讲备注（约 45 秒）**
架构上没有花活，就是个模块化单体。我认真考虑过微服务，然后意识到一个人同时维护三个服务的部署和日志是在给自己找事。
有两个细节值得说。第一，状态机的守卫我写成了纯函数，也就是说它不碰数据库、不碰网络，进来什么出去什么。这样做唯一的目的就是能穷举测试——17 条迁移乘 19 个动作，我可以把每种组合都跑一遍。
第二，时钟是注入的。所有跟时间有关的判断都不直接调系统的 now，而是从外面传进来。不然我没法测"刚好 45 分钟"和"45 分零 1 秒"这两种情况。

## 第 8 页 · 数据模型：14 张表，27 条索引

**标题**：索引不是越多越好，是每条都要说得出服务哪个查询

- 14 张表：用户 / 地点 / 订单 / 进度流 / 推送 / 评价 / 争议 / 治理 / 配置 …
- 27 条索引，其中 **5 条部分索引**（带 `WHERE` 条件），比如：
  - 进度流反向扫：只索引"接单人证据类事件"，取最后一条走到索引就停
  - 大厅可见单：只索引 `status = 'PENDING'` 的行，已完成的单不进索引
- **`seq` 并发分配**：进度流序号不用全局自增，按订单分段用 `UPDATE ... RETURNING` 分配，保证同一订单事件严格有序
- **CAS 乐观锁**：`UPDATE ... WHERE id = ? AND status = ? AND version = ?`，`rowcount != 1` 就是并发输了
- **约束名映射**：数据库唯一索引冲突不抛 500，按约束名翻译成具体业务码

**配图建议**：左侧 ER 图局部（用户—订单—进度流三张表），右侧四条要点；部分索引用高亮框标出 `WHERE` 那一行。

**演讲备注（约 40 秒）**
索引这块我给自己定了个硬要求：每建一条索引，都要在文档里写清楚它服务哪个查询。写不出来就别建，因为索引也是要维护成本的。
5 条部分索引里我最满意的是进度流那条。查"最后一条接单人进度"的时候，如果索引里混着系统事件和发单人的催单，那就得扫一堆再过滤。把 `WHERE` 写进索引，取到第一条就能停。
另外序号那条也挺折腾的：如果用数据库自增，不同订单的事件会交错，同一个订单的序号也可能不连续。最后改成按订单分段分配，才做到既有序又能并发。

## 第 10 页 · 核心难点一：45 分钟双出口互斥

**标题**：一个"定义"没写清楚，会造出比原 bug 更糟的死锁

**场景**：接单人抢了单，然后人消失了。发单人被白白占用了时间。

**两条出口，必须互斥**

| 出口 | 触发条件 | 结果 | 谁扣分 |
|---|---|---|---|
| T17 自助取消 | **完全没有**接单人进度 + 距抢单 ≥ 45 分钟 | 订单取消 | 接单人 −3 分 |
| T16 失联投诉 | **已有**接单人进度 + 最后一条进度距今 ≥ 45 分钟 | 进争议，冻结待裁 | 待裁定 |

**踩到的坑**：如果"进度"定义得太宽——把发单人的"催单"也算进度——

```
第 10 分钟：发单人催单一次
  → 被算作「有进度」→ T17 永久关闭（要求"无任何进度"）
  → 但它刚重置了静默计时 → T16 要求静默 45 分钟，还要再等 35 分钟
  → 两条路同时不可走，比原来的 bug 更糟
```

**解法**：进度 = `action ∈ 白名单` **且** `actor_id = 接单人`

- 白名单：已取件 / 在路上 / 已送达 / 备注——只有**接单人自己产生的**才算
- 这个定义全项目只写一处，其他地方只引用，不许重写
- 两个守卫共用一次反向索引扫，同时返回"有没有进度"和"静默起点"

**配图建议**：上半页画时间轴（0 分 / 10 分 / 45 分三条刻度），下半页画两条出口的判定分支；把"死锁"那段用红框单独框出来。

**演讲备注（约 60 秒）**
这是我这个项目里最得意、也最惊险的一处。
接单人抢了单然后消失，发单人得有出路。我设计了两条：一条是完全没进度的时候可以无责取消，另一条是有进度但人静默了可以投诉。两条都要求等 45 分钟。
问题出在"进度"这个词上。我一开始写得很随意，觉得只要是订单上发生了点什么就算进度。
后来我在推演的时候发现：发单人在第 10 分钟催了一次单，如果催单也算进度，那"完全没进度"这个条件就永远不成立了，无责取消这条路永久关闭。同时催单又把静默计时清零了，投诉那条路还得再等 35 分钟。
结果就是两条路同时不可走。发单人什么都做不了，只能找客服。这比我一开始想修的那个 bug 还要糟。
最后的解法是把定义收紧：进度必须是接单人自己产生的、在四类白名单动作里的事件。而且这个定义全项目只写一处，别的地方只能引用。因为我发现只要允许重写，就一定会有人（包括 AI）在别处写一个"差不多"的版本。

## 第 11 页 · 核心难点二：并发抢单的三道闸

**标题**：100 个人抢同一单，只能有 1 个成功

```
闸 1  Redis + Lua 锁          挡掉 99% 的并发，O(1)
      两把锁：订单维度 + 用户维度，SET NX PX
      脚本缓存失效（NOSCRIPT）自动重载
                 ↓
闸 2  PostgreSQL（唯一正确性权威）
      pg_advisory_xact_lock(uid)   → 同一用户串行化
      count(在途单) ≥ 上限          → 40902
      UPDATE ... WHERE status='PENDING'  → 40901  ← CAS 才是裁判
                 ↓
闸 3  Idempotency-Key          挡手抖与网络重试
      命中且订单一致 → 回放首次 200
      命中但订单不同 → 40904
```

**为什么要第二道闸里的 advisory lock**（只看代码会觉得多余）

- `count(*)` 和 `UPDATE` 之间如果没有串行化，同一用户并发抢 5 单会**全部读到"在途 2 单"**，然后全部通过
- 按用户加 advisory lock，代价约 0.1 毫秒，单实例完全够用

**Redis 可靠吗**：不作为权威

- Redis 只做召回期预过滤，允许轻微漂移；抢单时一律以数据库计数为准
- 后台清理任务每 10 分钟用数据库重建 Redis 集合，发现漂移就写 WARN 日志

**验证判据（不是"看起来对"）**

```
pytest tests/test_grab_concurrent.py -k concurrent
100 并发抢同一单
→ SELECT count(*) FROM orders WHERE status='IN_PROGRESS' 必须 == 1
→ 其余 99 个必须返回 40901
```

**配图建议**：三道闸做成漏斗/三重门；右下角单独放一行判据代码（这是可信度最高的一张图）。

**演讲备注（约 60 秒）**
抢单是这类系统最容易写错的地方，因为它在你本地跑一次永远是对的。你一个人点，当然只有一个成功。
我用了三道闸。第一道 Redis 加锁挡掉绝大部分并发，快；第二道是数据库，它是唯一的裁判；第三道是幂等键，挡用户手抖和网络重试。
中间有个坑值得单独说：在途单数量限制。直觉写法是先查这个人在途几单，没超就更新。但这两个操作之间没有串行化，同一个人并发抢五单，五个请求会全部读到"在途两单"，然后全部放行。所以我在用户维度加了 advisory lock，把同一个人的抢单请求排队。
还有一个心态上的转变：我不再相信"跑一遍看起来对"。这一组测试的判据是写死的——一百个并发打完，数据库里状态是"进行中"的记录数必须等于一，其余九十九个必须返回同一个错误码。这行断言比我说十句"我考虑过并发"都有用。

## 第 12 页 · 核心难点三：三个 bug，都不在函数里

**标题**：单测只测零件，测不出装配错了
**副标题**：三个事故都发生在"全绿之后"

| # | 案例 | 症状 | 为什么测试没抓到 |
|:---:|---|---|---|
| 1 | 列宽太窄 | 真库 `INSERT` 直接报错 | 内存替身不校验列宽 |
| 2 | 在途上限失效 | 手上已有 3 单，还能抢第 4 单 | 测试手填 `OrderCtx`，没走过真实 SQL |
| 3 | **发单不落库** | **接口 201「发布成功」，刷新一下订单没了** | **测试绕过 HTTP 层，测不到事务边界** |

**一句一个修法**

- ① 宽度 8 装不下 9 个字符（`UNSETTLED` / `PUBLISHER` / `EXCELLENT`）→ 不是改宽度就完，而是加「列宽自检 + 新增列必须登记」的闸门；排查时顺带把 10 个枚举列统一放宽到 `varchar(16)`
- ② `count(在途)` 与 `UPDATE` 之间没有串行化 → 按用户加 advisory lock，把同一个人的抢单请求排队
- ③ `get_db_session()` 只 `close()` 从不 `commit()`，而 service 按项目约定（一个请求一个事务）也不提交 → **两边都不提交，每一条请求的数据都凭空消失**；修法是依赖里 `yield` 之后 `commit()`、异常 `rollback()` 再 `raise`

**案例 ③ 的代码（右下角小窗，等宽字体）**

```python
# 错：只关闭，从不提交
def get_db_session():
    db = SessionLocal()
    try:    yield db
    finally: db.close()

# 对：正常返回提交，异常整段回滚
def get_db_session():
    db = SessionLocal()
    try:
        yield db
        db.commit()          # 请求正常返回 → 提交
    except Exception:
        db.rollback()        # 任何异常 → 整段回滚
        raise
    finally: db.close()
```

**怎么发现的（这句只口播，不要放太多字到页面上）**
端到端脚本 31 项断言全绿之后，我多问了一句"库里到底有没有"——用 `psql` 查，最后一条订单 id 是 1172，往前 1171 也是我自己造的，再往前就断了。

**页面底部大字（字号最大，居中）**

> 三个 bug 有一个共同点：它们都不在函数内部，而在**函数与函数之间**。
> 单元测试擅长验证「这个函数算得对不对」，天生测不到「这条链路接没接上」。

**配图建议**
- 主体：四行表格（表头 + 三个案例），**第 3 行加红框**，其余两行用浅灰
- 右边：代码小窗（错/对两段上下对照）
- 左下：`【图 C：接口返回 201 与 psql 查不到该订单的对比截图】` —— 左半边是 `curl` 拿到 201 的响应，右半边是 `select * from orders where id=...` 返回 0 rows
- 底部：那句大字，上下留白要足，不要再塞其他元素

**演讲备注（约 75 秒）**
这一页是我今天最想讲的，因为它改变了我对"测试通过"这四个字的理解。我踩了三次，每次都是全绿之后才发现的。
第一次是列宽。文档里写 `UNSETTLED`，九个字母，我把列宽写成了八。为什么没抓到？因为单元测试用的是内存替身，它不校验列宽。
第二次是在途上限。规则是一个人最多同时接三单，但同一个人的五个并发请求会全部读到"在途两单"，然后全部放行。为什么没抓到？因为测试里我手填了一个上下文对象，根本没走真实 SQL。
第三次最狠。我的数据库依赖只做了一件事：用完 `close()`。而 service 层按约定也不提交。两边都不提交，结果是每一条请求的数据都凭空消失。发单接口返回 201，订单号生成了，页面也跳转了，刷新一下就没了。
为什么六百多个测试都没抓到？因为我的测试直接调 service，session 由 fixture 管，断言在同一个没有提交的事务里做——它验证的是"函数返回对不对"，不是"请求结束后数据还在不在"。
这个不是测试发现的。是端到端脚本三十一项断言全绿之后，我多问了一句"库里有吗"，然后直接开 psql 查，发现订单号断档。
**一句话：单测只测零件，测不出装配错了。**

**三层判据（这一页真正的重点，第 12 页三个 bug 各被一层挡住）**

| 层 | 手段 | 能抓到什么 |
|---|---|---|
| 函数层 | 守卫纯函数 + 状态×动作矩阵穷举 | 边界值算错、非法迁移没拒绝 |

| 真库层 | 迁移往返（升→降→升）+ 列宽自检 + 并发判据 | 列宽装不下、索引缺失、CAS 失效 |

**三个我认为比覆盖率更重要的做法**

- **断言要可判定**：不写"应该能抢到"，写 `count(*) == 1`
- **投影一致性**：状态枚举与事件流两套表示必须对得上，对不上说明有人绕过状态机直接改了状态
- **乱序跑一次**：`pytest -p tests.qa_shuffle_plugin`（默认不开，需要时手动开），暴露测试之间偷偷相互依赖

- `【图 B：闸门生效的红绿对比】` 放底部 —— 上半张全绿汇总行，下半张 `FAILED` 红字；这张图证明"闸门真的会红"

**演讲备注（约 50 秒）**
我不打算讲覆盖率，因为覆盖率可以刷。我讲这条测试是怎么分层的，因为上一页那三个 bug 正好一层被一层挡住。
最上面一层是函数层，守卫写成纯函数，状态乘动作穷举，边界值算错立刻红。
中间一层是最容易被跳过的一层：事务边界。做法很土——走真实 HTTP 请求，请求结束之后另开一个连接去查库。就这一步能抓到"没提交"，因为你在同一个会话里查，提交不提交都查得到。
最下面一层是真库层：迁移要能升上去、也能降回来，列宽自检，并发判据。
现在的全量数字是 707 个用例通过，六百一十五加九十二，截至十月二十九号。我不建议在答辩时强调这个数，因为它每天都在变；但它能证明一件事：这些结论不是我说的，是跑出来的。
第三个最简单也最有用：断言要写成可判定的。不写"应该能抢到"，写"数据库里状态是进行中的记录数等于一"。

## 第 15 页 · 开发方法：我是怎么和 AI 配合的

**标题**：AI 写代码很快，但它有个致命习惯——会自己给自己发合格证

- **角色分工**：我负责"判据"，AI 负责"实现"
  - 我写清楚：要什么、不许做什么、怎么算通过（可判定的断言）
  - AI 写：状态机、守卫、仓储、迁移、测试
- **有效的一句**：「先写出判据，再写实现。判据必须是一条能跑、能红、能绿的断言。」
- **翻过的三次车**：AI 每次都说"测试全部通过"，三次都是全绿之后才露的（第 12 页）
  - 原因：它验证的是替身，不是真实边界
  - 从此加了一条硬规矩：**任何涉及数据库的结论，必须在真实 PostgreSQL 上复现一遍**
- **回退点**：每完成一个可验收的小块就打一个标签，出问题整体退回，不在泥潭里修

**配图建议**：左右两栏对照（我做什么 / AI 做什么）；中间一条竖线，线上标一句"判据在这里产生"；右下角放一个 `git log` 截图（有 22 条提交，含多条 `fix:`）。

**演讲备注（约 45 秒）**
我用了 AI 辅助，但我慢慢发现它有一个很危险的习惯：它特别愿意给自己发合格证。
你让它写代码，它写完会说"测试全部通过"。这句话在大部分时候是真的——它写的测试确实通过了。但问题是，它写的测试验证的是它自己造的那个替身。
第 12 页那三个事故都是这么来的。当时全绿，一接真库就露。
所以后来我换了个配合方式：我负责出判据，它负责实现。判据必须是一条能跑、能变红、也能变绿的断言。判得对不对由这条断言说了算，不由它说"我觉得可以了"。
这部分我在另一份《技能分析》里拆得很细，包括我实际用的三段 prompt。

## 第 16 页 · 个人收获

**标题**：三件我原来不会、现在会了的事

- **第一件：把模糊需求翻译成可判定的断言**

  - 现在我会主动问自己："这个结论是在什么环境里得出的？"
- **第三件：设计就是给"不顺利"留位置**
  - 顺利的流程两小时能写完，45 分钟双出口写了一个下午
  - 但产品好不好用，取决于最坏的那条路径

**演讲备注（约 45 秒）**
三件事，我尽量说得具体一点。

**标题**：如果还有时间，我会按这个顺序做

| 优先级 | 事项 | 为什么是它 | 大概工作量 |
|---|---|---|---|
| P0 | **学号认证** | 没有它任何人都能注册，这是致命的 | 3–4 天 |
| P0 | 消息推送 | 现在接单人得一直刷大厅，体验是断的 | 3–5 天 |
| P1 | 评价体系 | 表结构已定，缺业务逻辑 | 2–3 天 |
| P1 | 纠纷仲裁后台 | 状态机两条迁移已就绪，缺运营界面 | 4–5 天 |
| P2 | 运营管理后台 | 封禁、看数据 | 3–4 天 |
| P2 | 多校区 | 现在把校区写死在配置里 | 2 天 |

- 顺序的理由：**先说"谁能用"，再说"能不能收到"，最后才是"好不好用"**
- 这次没做的四项，在 PPT 和口播里都会明说没做

**配图建议**：表格即可，P0/P1/P2 用三档颜色；右侧留一列空白，现场可以手写"如果只剩一周我会砍掉哪些"。

**演讲备注（约 35 秒）**
后续规划我按"先说谁能用、再说能不能收到、最后才是好不好用"排的。
学号认证排第一，因为现在任何人都能注册，这在真实场景里是不能上线的。推送排第二，因为现在接单人必须一直盯着大厅刷，这不现实。
评价和仲裁的表结构已经定好了，状态机里对应的两条迁移也写完了，缺的是业务逻辑和界面。所以如果还有时间，这部分是投产比最高的。
