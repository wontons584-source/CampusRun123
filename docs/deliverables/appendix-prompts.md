# 附录：三段可直接复制的 Prompt

> 用途：配合《技能分析》正文使用，给"想照着做一遍"的人直接抄。
> 说明：三段都脱敏过，把 `<尖括号>` 里的内容换成你自己的项目即可直接运行。
> 用法：**整段复制**，不要只复制其中一段——每段里的约束部分是配套的，拆开用效果会打折。

**一个使用前提**：这三段 prompt 都假设你在一个支持长上下文的对话式 AI 里用（ChatGPT / Claude / 通义 / 豆包均可）。如果你用的是 IDE 内的补全型工具，效果会差一些，因为它们不擅长"先想清楚再写"。

---

## Prompt 1 · 让 AI 做架构设计

### 这段用来做什么

项目刚起步、只有一个模糊想法的时候用。目标不是让它给你一套架构，而是让它**逼你把 5 件必须想清楚的事写下来**：模块边界、表结构、索引依据、并发风险、不做什么。

它最容易翻车的地方是"给你一套放在哪个项目都成立的方案"。所以这段 prompt 里塞了四个"防"：防跑题、防堆索引、防套话、防编造。

### 复制这一段

```
【背景】
单人开发，工期紧（周末两天做后端内核）。技术栈锁定：
Python 3.11 + FastAPI + SQLAlchemy 2.0(async) + PostgreSQL 16 + Redis 7。

【任务】
为"<你的系统名，一句话说明它解决什么>"的订单系统做架构设计。
请只输出以下 5 项，不要写代码：
1. 模块划分（每个模块一句话职责 + 边界，说明哪些是纯函数、哪些碰 IO）
2. 核心表的 DDL 要点（字段、类型、必须的约束）
3. 索引清单：每条索引必须写明"服务哪个查询"，写不出查询的索引不要列
4. 关键流程的并发分析：列出所有"两个请求同时到达会出错"的位置，
   每个位置说明用什么机制保证（DB 约束 / 行锁 / 乐观锁 / 分布式锁），
   并说明为什么不用其他机制
5. 明确的"不做"清单：本次不做什么，以及如果不做会有什么后果

【约束】
- 不要引入消息队列、不要微服务、不要 CQRS（一个人维护不了）
- 每个设计决定必须给出"为什么不用另一个方案"的一句话理由
- 如果某项信息不足以做决定，列到"待确认"里，不要自己假设

【格式】
表格优先，每个判断后面不要写"最佳实践"，要写"因为……所以……"。
```

### 四个"防"分别起什么作用

| 约束 | 防什么 |
|---|---|
| 只输出 5 项、不要写代码 | 防它直接开始写代码，把架构部分跳过 |
| 每条索引必须写明服务哪个查询 | 防它堆一堆索引显得专业，你事后没法删 |
| 每个决定要写"为什么不用另一个" | 防套话。它必须把被否掉的方案说出来，你才有得判断 |
| 信息不足列到"待确认"，不要假设 | 防编造。这一条通常会给你 2–4 个你确实没想过的问题 |

### 我实际拿到的"待确认"（三个都是真问题）

1. 一个接单人最多同时接几单？（这条后来变成了 `order.max_inflight` 配置）
2. Redis 和数据库谁是权威？（后来定成：Redis 只做预过滤，数据库是唯一裁判）
3. 争议恢复后，原来的超时时刻怎么算？（后来定成：不重写送达时间，只重算到期时刻）

### 验收要点

- 拿到输出后，先看第 3 项（索引清单）和第 5 项（不做清单）。这两项写得含糊，说明这次对话没起作用，重来
- 第 4 项里的每个并发位置，你都应该能自己复述一遍"为什么这里会错"

## Prompt 2 · 让 AI 写状态机守卫

### 这段用来做什么

写业务规则里**最容易写错的那部分**：带时间窗口、带角色限制、带互斥条件的判断逻辑。

这类代码的特点是：测试用例写少了会漏边界，写多了人写不动。所以核心策略是把它做成**纯函数**，然后穷举。

### 复制这一段

```
【任务】
实现订单状态机的守卫函数。守卫必须是纯函数：
签名 (order, actor, payload, cfg) -> bool，不碰数据库、不碰网络、不读全局时钟。
数据不够就抛业务异常，不要返回 False 含糊过去。

【唯一事实来源】
状态迁移表见附表（<N> 行）。你必须逐行实现，编号对齐，不许合并、不许新增。

【本次只做这两个守卫，都是"<角色>"才能触发的零人工出口】
A. <出口一名称>（迁移 T<N>）：进入"<目标状态>"，<副作用>
   条件：订单当前"<某状态>" AND 操作者=<某角色>
         AND <关键条件一>
         AND <关键条件二，通常是时间窗口>
B. <出口二名称>（迁移 T<N>）：进入"<目标状态>"并<副作用>
   条件：订单当前"<某状态>" AND 操作者=<某角色>
         AND <关键条件一>
         AND <关键条件二>

【术语定义（必须严格遵守，不许在别处重新定义）】
「<核心术语>」= 动作 ∈ {<白名单动作>} 且 操作者 id = <某个 id>。
注意：<哪些动作虽然看起来像但不算>。
原因：如果把 <某动作> 也算进去，则 <条件 A> 永久不成立，
      而 <条件 B> 的计时刚被重置还要再等 N 分钟，
      两条出口同时不可走 —— 这比原 bug 更糟。

【边界必须显式处理】
- 恰好 <N> 分 00 秒 → 允许
- <N-1> 分 59 秒 → 拒绝，错误码 <码>，文案必须说明还差多少
- <异常入参：从未进入该状态 / 已在终态> → 拒绝，错误码必须是具体的那个，不要笼统 400

【输出】
1. 两个守卫函数（含类型标注）
2. 参数化测试：正常 / 边界下 1 秒 / 边界 / 边界上 1 秒 / 角色不对 / 状态不对，各一条
3. 一段 100 字以内的注释，说明"为什么<核心术语>要限制操作者"
```

### 关键在"术语定义"那一段

第一次我写这条 prompt 时，只写了「进度 = 接单人的动作」，没写括号里那句原因。结果它在另一个文件里把所有动作都算进去了——因为在它的理解里，"备注"也是动作。

后来学到的办法：**不只告诉它定义是什么，还要告诉它理解错了会发生什么。** 不给它理由，它会用自己的一套逻辑把空白补上。

### 为什么必须是纯函数

因为纯函数才能穷举。17 条迁移 × 18 个动作 = 306 种组合，纯函数可以在毫秒级跑完；一旦里面碰了数据库，这 306 条测试就得起 306 次事务，没人会跑。

### 验收要点

- 看它给的测试用例里有没有 `恰好 N 分 00 秒` 和 `N-1 分 59 秒` 这两条。没有就退回
- 自己写一条"角色不对"的用例手测一遍，很多人会漏
- 检查守卫有没有偷偷调用 `datetime.now()`。有就退回，改成从入参取

## Prompt 3 · 让 AI 抓自己的 bug

### 这段用来做什么

在你怀疑"某类问题还会复发"的时候用。目标不是让它"再检查一遍"（那句话没有信息量），而是让它**造一道能失败的闸门**。

### 复制这一段

```
【任务】
我现在怀疑"<某类问题，例如：枚举列宽不足>"还会复发。请你设计一个
**纯<层次>层**的测试文件，不依赖<外部依赖>、每次 <测试命令> 都会跑，
用来把这类问题钉死。

【必须覆盖的 5 条断言】
1. <核心断言：每个枚举列 最长取值长度 <= 列声明长度>
2. <闸门断言：每一列 X 类型 必须被登记为"枚举列"或"自由文本列"，
   漏登记直接失败（这是防止新增列时遗忘的闸门）>
3. <自洽断言：登记表里的每个键，必须真实存在于定义中（防改名后失配）>
4. <一致断言：登记表里的值，必须和生成列的 SQL 表达式文本一致
   （防"登记表自己写错、测试跟着错"）>
5. <预警断言：把当前各列的剩余余量钉成快照，新值吃掉余量时失败并提示"该加宽了">

【硬约束】
- 不许 connect 数据库、不许 mock 数据库、不许读迁移文件
- 只允许 import <你的模型模块>
- 每条断言失败时，报错信息必须包含：<列名 / 当前宽度 / 最长取值 / 差多少>

【验收】
请你先故意把<某一列>改小 1，跑一次给我看它必须失败；
再改回来，跑一次给我看它必须通过。两个结果都要贴出来。
```

### 最后那一段是整条 prompt 的重点

只让它"写测试"，它会写一堆必然通过的断言——你跑一下全绿，就信了，但它可能根本没测到你担心的事。

要求它**先故意造一个失败**，会逼它自己验证"我这个测试真的有效"。这个技巧我后来用在所有由它写的测试上。

### 第 2 条断言为什么是核心

前 1/3/4/5 条都是修当下，只有第 2 条是防未来：它让"新增一个字段"这个动作必须先过一道闸。没有它，下一个人加字段时照样不会想到宽度这件事——包括你自己。

### 验收要点

- 必须看到它贴出"故意改坏 → FAILED"的输出。没贴就是没做，退回
- 自己再改坏一个**它没用过的**字段，看能不能被抓到。能抓到才算这道闸门真的生效

---

## 三段 prompt 的共同点（比单段更重要）

1. **每条都要求它产出"可判定的东西"**：一份清单、一条断言、一个能跑的结果
2. **每条都写了"不许做什么"**：不写代码、不许合并迁移、不许连数据库
3. **每条都要求它解释或自证**：为什么不用另一个方案、为什么这样定义、先失败给我看
4. **每条都留了"我不知道"的出口**：待确认、抛异常而不是返回 False、报错要写差多少

第 4 点最容易被忽略。**给 AI 一个诚实的出口，比逼它给答案有用得多。**
